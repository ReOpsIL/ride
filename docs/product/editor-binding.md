# Editor binding: which view belongs to which document

An `EditorHostView` is bound to exactly one `BufferDocument` (`EditorHostView.bind`), and a document is shown by at most one host. The host is the only object allowed to copy text between the two (`bind` view ← document, `capture` document ← view).

Rules for app code:

- Never pair `activeBuffer`/`activeID` with `EditorPanes.shared.focusedView`. `PaneLayout` changes synchronously; SwiftUI builds the matching host later, so between the two the focused host still shows the previous document. Use `EditorPanes.shared.host(bound: buffer)` to reach a document's view, or `AppState.focusedEditor` to get a view and its own document together.
- Text that must land in a document (format result, reload from disk, project replace) goes through `AppState.deliver(_:to:disk:)`; caret moves after opening a file go through `AppState.jump(to:in:)` or `openFile(_:at:)`. Both store the pending value on the `BufferDocument` and apply it when its host exists, so a result never lands in another pane.
- Saving, autosave and close prompts take the buffer they act on (`save(_:)`, `autoSave(_:)`, `confirmClose(_:)`), not the active one.
- `EditorPanes` focus follows `PaneLayout.focusedID`: the focused `PaneColumn` adopts its host on every update, and `makeFocusedEditorFirstResponder` on a pane without a host claims first responder for the host that attaches next.
- Workspace capture (`captureWorkspace`) captures every bound host and runs inside the debounced save, not on every caret move.
- Undo history is per document (`BufferDocument.undo`), so it survives tab switches and is not shared between split panes; records resolve the pane that shows the buffer when they run, so a pane rebuilt by SwiftUI inherits the history.
- Demo mode (`--demo`) disables workspace persistence; a self-test step that exercises the persistence hook must call `state.captureWorkspace()` itself.

Undo, grouping and records:

- `BufferDocument.undo` is a `BufferUndo`; its `manager` is built by `UndoStep.manager()` with `groupsByEvent = false`. AppKit's per-event grouping closes a top-level group from `-[NSApplication _handleEvent:]` only, so edits applied from timers, engine callbacks or the self-test (no NSEvent between them) all land in one group and a single ⌘Z reverts every one of them. That is the cause of the 2026-09-20 self-test undo flake.
- The editor owns the undo **records**, not only the group. `RideTextView.undoManager` returns nil, so AppKit registers nothing: its `NSUndoTyping` operation edits the text storage inside `-[NSTextStorage endEditing]` and then calls `didChangeText` on the text view it finds through the storage's `NSLayoutManager`. The views are TextKit 2 (`RideTextView.makeTK2`), the storage has no layout manager, and the call never happens, so an AppKit undo changed the text behind the coordinator's back: `document.text`, breakpoint marks, underlines, highlights, folds and the engine session all kept the pre-undo state. `allowsUndo = false` does not stop that registration; vending no manager does. The Edit menu reaches undo through `RideTextView.undo(_:)`/`redo(_:)` (`RideTextView+Undo.swift`), which drive `BufferUndo.manager`, and `validateUserInterfaceItem` enables the items.
- One group is one record. `EditorPane.Coordinator.textView(_:shouldChangeTextIn:)` calls `BufferUndo.open`, which snapshots `document.text` and opens the group; `textDidChange` updates `document.text` and calls `BufferUndo.close`, which diffs snapshot against current text (`UndoEdit.inverse`, on `TextDiff.minimalEdit`) and registers one `UndoRecord` before ending the group. A record holds the range the edit occupies now and the text it replaced, so a batch of `TextChange`s is a single inverse edit and the order the changes were applied in does not matter.
- `UndoRecord.revert` resolves the pane bound to the document (`EditorPanes.host(bound:)`) and applies its inverse through `RideTextView.replaceText`, the same path as any other edit. Undo therefore shifts breakpoints, underlines, highlights and the engine session like a normal edit, and the pipeline registers the inverse of the revert while the manager is undoing, which is the redo record.
- A typing run is one step: `BufferUndo` keeps the record of a single-character insertion and extends it while the next insertion is one character at its end (`UndoEdit.extended`), instead of registering a second record. `RideTextView.breakUndoCoalescing` calls `BufferUndo.close` with nothing pending, which ends the run, so a coalescing break is a step boundary.
- Every programmatic edit goes through `RideTextView.applyChanges` (`EditorCommand.apply`, `RideTextView.applyTyping`, `EditorHostView.replaceText`), which runs the whole batch inside `BufferUndo.batch`: the group stays open and the per-change `close` is suppressed until the batch ends, so the batch is one undo step.
- While the manager is undoing or redoing, `BufferUndo` opens a group only if Foundation has none, and ends only the groups it opened itself.
- Buffers with no pane (background rename) keep the whole-text records of `BufferTextUndo`, which groups with `UndoStep.perform`.
